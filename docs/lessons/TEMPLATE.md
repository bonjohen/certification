## The Lesson

<!--
1-3 sentences. State the core takeaway as a general principle, not a 
project-specific fact. A reader should be able to apply this to their 
own work after reading only this section.

Good:  "When migrating a data format, the key risk is proving the new 
        format produces identical behavior — not the conversion itself."
Bad:   "We migrated XML to JSON in the certification project."
-->


## Context

<!--
Set the stage so the lesson makes sense to someone outside the project.
Answer: What kind of system? What scale? What constraints? Why did this 
situation arise?

Keep it to one paragraph. Use concrete numbers (file counts, question 
counts, provider counts) but avoid internal file paths or class names 
that require codebase access to understand.
-->


## What Happened

<!--
A numbered sequence of events: what was tried, in what order, and what 
the outcome was at each step. Include both successes and failures.

Focus on decisions and their consequences, not implementation minutiae.
If a tool or script was written, name it and say what it did — don't 
paste the source code here (that goes in the Examples section if needed).

Aim for 4-8 steps. If you need more, the lesson might be two lessons.
-->


## Key Insights

<!--
Bulleted list of reusable observations. Each bullet should:
  1. Start with a bold statement (the insight itself)
  2. Follow with 1-2 sentences of explanation or evidence

Target 4-6 insights. Fewer means the lesson is thin. More than 8 means 
some are repetitive or the lesson should be split.

Each insight should be actionable: a reader should be able to change 
their behavior based on it. "This was interesting" is not an insight.
"Always do X because Y" is.
-->


## Examples

<!--
OPTIONAL. Include when concrete examples make the lesson significantly 
clearer. Delete this section entirely if examples aren't needed.

Show before/after, good/bad, or worked/failed comparisons. Use code 
blocks, tables, or side-by-side comparisons as appropriate. Keep 
examples minimal — just enough to illustrate the point.

If including code, use generic/simplified versions rather than copying 
verbatim from the codebase. The example should be understandable 
without project-specific context.
-->
