# Project Review

**Date:** 2026-05-08
**Scope:** full
**Project:** certification-quiz
**Reviewer:** Claude Code

## Executive Summary

The codebase is in good health after recent cleanup (XML removal, Atlas migration, lessons system). The most significant finding is inconsistent CSP coverage: only 2 of 15 HTML pages have Content Security Policy headers, leaving the quiz page (which uses innerHTML) and all provider pages unprotected. Secondary findings are stale artifacts from early project phases still tracked in git, and `results-app.js` having 0% test coverage.

## Findings

### [HIGH] F-01: Inconsistent Content Security Policy coverage

**Category:** Security
**Evidence:**
- Only `results.html` and `lesson.html` have CSP meta tags
- `quiz.html` — the page that uses `innerHTML` to render exam content — has NO CSP
- `index.html`, all 10 provider pages, and `lessons.html` also have no CSP

**Impact:** The quiz page is the highest-risk page (renders user-facing content via innerHTML from JSON data). Without CSP, if the sanitization in `sanitizeHTML()` has a bypass, injected scripts would execute. The provider/index pages are lower risk (no dynamic content rendering) but still lack the defense-in-depth layer.

**Fix:** Add CSP meta tag to `quiz.html` matching the pattern used in `results.html`: `default-src 'self'; script-src 'self' https://esm.sh; connect-src 'self' https://esm.sh; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:;`. For static provider pages that don't use esm.sh, a stricter `script-src 'self'` suffices.

### [MEDIUM] F-02: results-app.js has 0% test coverage

**Category:** Tests
**Evidence:**
- Coverage report shows: `results-app.js | 0 | 0 | 0 | 0 | 1-479`
- No test file exists: `grep -rn "results-app" tests/` returns nothing

**Impact:** The results page renders per-question breakdowns, category analysis, and timing data. Any refactoring or bug fix has no safety net. Given it uses `innerHTML` with `sanitizeHTML()`, the sanitization path for this page is also untested.

**Fix:** Create `tests/unit/results-app.test.js` or `tests/integration/results-app.integration.test.js` testing the core rendering functions (score calculation, category breakdown, detail list rendering). Priority: test the `sanitizeHTML` usage paths in this file.

### [MEDIUM] F-03: Stale directories tracked in git — plans/, prompts/, tools/

**Category:** Dead Code
**Evidence:**
- `git ls-files plans/` → `plans/AWSPlan.md` (an early-project plan from before multi-provider support)
- `prompts/` — empty directory tracked in git
- `tools/` — empty directory tracked in git

**Impact:** These are noise in the repository. `plans/AWSPlan.md` references `index2.html` which never existed (the actual implementation used `aws.html`). Empty directories and orphan plans confuse new contributors.

**Fix:** Remove from git: `git rm -r plans/ prompts/ tools/`. Add to `.gitignore` if they might be recreated locally.

### [MEDIUM] F-04: system/index.html and docs/redesign/ are stale reference files

**Category:** Dead Code
**Evidence:**
- `system/index.html` — Atlas design system reference page, not linked from any navigation
- `docs/redesign/CertificationRedesign.html` + `docs/redesign/CertificationRedesign_files/css2` — original redesign mockup HTML

**Impact:** These served their purpose during design (reference implementation and mockup) but are now dead weight. The system reference page could confuse someone into thinking it's a production page.

**Fix:** Remove `docs/redesign/` directory and `system/index.html` from git. The design system is documented by the live pages themselves.

### [MEDIUM] F-05: progress-tracker.js has 60.89% coverage with untested migration logic

**Category:** Tests
**Evidence:**
- Coverage: `progress-tracker.js | 60.89 | 84.84 | 75 | 60.89 | ...34-150,153-170`
- Lines 134-170 are likely the format migration and history management code paths

**Impact:** Storage format migration is critical — if it breaks, users lose saved quiz progress. The untested paths are exactly the high-risk code (handling old formats, edge cases).

**Fix:** Add test cases in `tests/unit/progress-tracker.test.js` covering: old storage format detection, migration to new format, corrupted data handling, and history record management.

### [LOW] F-06: quiz.html CSP inconsistency with results.html

**Category:** Consistency
**Evidence:**
- `results.html` CSP: `script-src 'self' https://esm.sh` (no `'unsafe-inline'`)
- `lesson.html` CSP: `script-src 'self' 'unsafe-inline' https://esm.sh` (has `'unsafe-inline'`)
- Two different CSP policies for pages in the same application

**Impact:** Inconsistent security posture. If one page needs `'unsafe-inline'`, the others probably do too (all have inline `<script>` blocks for theme toggle). If they don't need it, `lesson.html` shouldn't have it.

**Fix:** Standardize on a single CSP policy for all pages. Since all pages use inline `<script>` for the theme toggle, either all need `'unsafe-inline'` or all should externalize the theme script to a `.js` file and drop `'unsafe-inline'`.

### [LOW] F-07: README still references only 4 providers in "Supported Exams" table

**Category:** Documentation
**Evidence:**
- `README.md` lines 16-57: lists Azure (8), AWS (7), GCP (10), Anthropic (1) — total 4 providers
- Actual site has 10 providers (CompTIA, ISC2, GitHub, Databricks, NVIDIA, Cisco are missing)

**Impact:** New contributors or users reading the README get an incomplete picture of the project's scope.

**Fix:** Add the 6 missing providers to the "Supported Exams" section, or replace the detailed tables with a summary pointing to the live site.
